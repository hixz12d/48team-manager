# UI 第二批实施记录

对应 `UI改动大纲.md` 第 13 章第 2 批：方案 A 的共享任务进度。仅本地实现与隔离验证，未部署。第 1 批及插件已有改动均保留。

## 已完成

- `runtime-store.js` 提供页面级 `window.Team48Runtime`：全站唯一 `/api/runtime/status` 读取入口。有任务/待人工/本地未返回请求时 2 秒，没有时 15 秒；复用现有轮询退避、visibility 和 pagehide/pageshow 行为。
- 总览 runtime 和自动轮转控制订阅同一个来源；旧 `watchInviteProgress` 独立轮询删除。计时使用一个页面级时钟，阶段没有变化时保留按钮 DOM 和键盘焦点。
- `task-progress.js` 统一紧凑分段条与标准步骤条：团队卡、团队抽屉顶部、全站顶栏任务中心、任务详情。浏览器子阶段归入主阶段；OAuth 内的浏览器步骤留在授权阶段。
- 团队卡在任务运行时隐藏手工到期/次数行；成功/取消结束 10 秒后恢复。失败/部分成功/需人工保留提示。抽屉保留结果，提供“收起”。
- 顶栏显示进行中和需人工数量，任务中心包含活动任务与最近 5 条结束记录。侧栏状态取真实 runner 心跳，读取失败明确显示旧状态。
- 邀请、补充、轮转、踢人同步 POST 在发送时进入本地待确认状态，随后匹配新的 runtime 公共 ID。关闭抽屉不终止轮询，完成后不强行重新打开抽屉。刷新页面从服务器 runtime 恢复。
- 邀请/补充/轮转提交后收起表单，步骤区接管。取消调用现有接口，先确认已发出的邀请不会自动撤回、已产生变更不会自动恢复。取消回执不因迟到的快照倒退。
- 详情使用 `step_label` 和历史 `log.stage`，最近 8 条日志默认折叠；技术详情显示 error_code/result，敏感名称字段遮盖。只对后端 `can_retry` 明确允许的任务提供重试。
- `summarizeOperationResult` 共用于任务进度、`handleActionResult` 和 `finishCurrentOperation`，描述真实的入组、授权、推送、暂停及轮转部分完成结果。没有实际席位/计数数据时不造数字。
- 后端仅扩展只读呈现：`presenters.py` 统一阶段表，由详情和 runtime 下发；runtime 增加 allowlist 阶段观察记录和取消能力，活动列表上限由 8 提高到 200，覆盖日常 10–40 个团队。日志原文、输入参数和秘密不进入 runtime。

## 与大纲原示意的区别

- 踢人的现有业务顺序是先确认官方离组，再暂停已绑定的远端调度。阶段表按实际源码顺序排列，不为匹配草图改业务。
- `invite_mail` 是发送邀请阶段的子阶段，保持入组 7 个主阶段。阶段位置不是时间百分比。
- 入组并不保证已授权或已推送；例如 `pushed: false` 明确显示“本轮未推送 Sub2API”。
- 历史和 runtime 没有逐步完成证据时显示“已记录”或“待确认”。不把到达阶段当作完成，也不把没有日志当作跳过。逐阶段耗时、完整步骤记录仍受现有后端数据限制。
- 任务接口仍同步执行；本批没有进行方案 B 的异步化、业务取消点或流程重构。
- 第 2.7 章的表单/轮转下拉、账号行信息重排属于第 3 批；本批没有顺带改这些界面。
