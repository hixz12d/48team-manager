# 自动轮转：错峰探测 / 401 重授权 / 踢拉

交接文档。下一窗口按本文实现，不要重新发明语义。

触发背景：席位看板上一大片母号显示「429 4天」、若干子号「401 失效」。用户确认昨晚周额度已经重置，真实 7 日用量是 0，账号能打。看板读的是 Sub2API 列表缓存里的 `codex_7d_used_percent`，没有定时强制探测，也不会在额度恢复后打开 `schedulable`。

目标分三层，必须按顺序落地，默认只开第 1 层。第 2、3 层各自独立开关，默认关。

```
1. 错峰探测 usage → 额度恢复则清 Sub 本地 429 锁并打开调度
2. 子号 401 → 自动接码重新授权（deactivate 停手）
3. 封禁 401 或 7 日周限满 → 过 vacancy 闸才踢拉
```

本仓库是自用轮转工厂，不是客户席位后台。术语以根目录 [`CONTEXT.md`](../CONTEXT.md) 为准。

HME：空邮箱拉人向 VPS `icloud-hme` 领未占用别名，成功后只打 `accounts.json` 本地标签，不写 iCloud。不要把本机 `data/accounts.json` 当占用库，不要为打标去动 Apple。

踢人语义：踢人不删子号记录，进 `standby`。踢人 ≠ 计费席位已释放。`policy_notice` / `billing_notice` 没有稳定公开语义。`is_safe_to_refill()` 为假时禁止自动补位；核对 Billing 后才能强制补位。

凭证语义：Access Token 过期先换票，不要当封禁。RT / Session Token 失效才标过期或封禁。

不要把质保自动踢人（兑换码过期清客户）和工作区轮转（本功能）混成同一个开关、同一套任务。

部署、SSH、付费、破坏性操作、扩大到第 3 层默认开启前，必须先说明影响并取得用户确认。本机改代码和单测可以做；上机部署先问。

## 1. 用户要的三件事

### 1.1 错峰探测 usage，能用就开调度

现象：看板母号几乎全是「429 4天」，但昨晚周额度已重置，真实用量 0。

原因：[`app/services/sub2api.py`](../app/services/sub2api.py) 的 `_schedule_state()` 用列表字段 `codex_7d_used_percent >= 100` 打「429」标签。`attach_usage_costs()` 调 `/api/v1/admin/accounts/usage/batch` 时 `force: False`，只给消费金额，不刷新额度，也不写 `schedulable`。席位页刷新只读缓存（`_STATUS_CACHE_TTL = 45s`，`_USAGE_COST_TTL = 90s`）。

要求：

- 大约每 1 小时扫一轮，但**禁止所有账号同一秒齐射**。
- 按账号把探测摊进窗口（建议 60 分钟）。每号固定偏移：例如 `hash(account_id) % window_sec`，或持久化 `next_probe_at`。
- 探测对象是 Sub2API 账本上的 Team 相关账号（母号 + 子号），不是 ChatGPT `/me`。现有 `probe_access_token()` 只探 token 死活，解决不了「429 标签过期」。
- 探测后若 7 日用量未满、5h 未满、账号不是 401/403/phone/error：先清掉 Sub 本地「限流中 / 429」锁（`clear-rate-limit`），再把 `schedulable` 打开。
- 5h 满：只暂停调度，**不要踢人**。
- 7d 满：保持/改为不调度，标签继续「429」；踢拉是第 3 层的事。
- 失败要退避，不要对同一号狂刷。

### 1.2 子号 401 自动接码重新授权

现象：`.2026.15`、`new2`、`.2026.28` 等子号「401 失效」。OAuth token 掉了，不是周限额。

已有能力：iCloud 子号只要有邮箱读码（pickup 或 Cloudflare）、号码库、静态 ISP，就可以自动跑完 Playwright OAuth 并写回 Sub2API。本地没存密码时走一次性验证码，不要因此改手动。入口是人手点「重新授权」。

要求：

- 定时/探测发现子号 401 后入队，不再等人点。
- 继续走现有 `auto_reauth_plan()`：只自动 iCloud 子号。母号、Gmail 仍弹窗，不要偷偷开浏览器去登 Gmail。
- 接码走号码库 [`app/services/phone_pool.py`](../app/services/phone_pool.py)，不要每次手填一行。
- 浏览器流程必须识别 **deactivate / account has been deactivated**。命中就停，不要换号死磕。这种号交给第 3 层。
- Playwright 不能十几条 401 一起开。全局串行，或最多 1 条浏览器任务。已有 `onboard_jobs.active_job_for_email()`，按邮箱去重。
- 同一子号失败要冷却，避免号码库被烧光。

### 1.3 封禁 401 或 7 日周限满了自动踢拉

用户逻辑：401 若是封禁而不是掉票，或 7 日额度用尽，这个号短期内没用，应踢掉并从邮箱库拉新号。

现有 `rotate_one()` **不是**这条路径。它按 `joined_at + cycle_days`（默认 7 天）找到期子号，再 1 踢 1 拉。到期轮转 ≠ 额度轮转 ≠ 封禁轮转。

要求：

- 先分诊：掉票 401 → 第 2 层重授权；deactivate / 确认封禁 → 本层踢拉；7d 满且探测确认仍满 → 本层踢拉。
- 踢人走 `onboard_service.kick_to_standby()`，进 `standby`，不删记录。
- 补位必须过 [`is_safe_to_refill()`](../app/services/vacancy.py)。账单回执不清就停，写入原因，等人勾选强制补位。不要把「强制补位」做成定时任务默认值。
- 拉新号走现有 `invite_and_onboard()`：空邮箱领 HME，号码库接码，对账成功才推 Sub2API。
- 冷却：刚踢的号 `KICK_COOLDOWN_SECONDS = 10 * 60`，不要立刻再拉回来。
- 本层默认关。没用户明确授权不要打开，更不要上机默认启用。

## 3. 建议实现

新代码优先放独立服务，例如 `app/services/auto_rotate.py`（名字可改，但不要把逻辑塞进 `warranty.py`）。调度注册留在 `app/main.py`，设置表单留在系统中心。

### 3.1 第 1 层：错峰探测 + 开调度

建议设置键（可微调，但要有开关和窗口，不要写死）：

- `usage_probe_enabled` 默认 `true` 或先 `false`，上机前问用户
- `usage_probe_interval_minutes` 默认 `60`
- `usage_probe_stagger_minutes` 默认 `60`（把本轮账号摊进这么多分钟）
- `usage_probe_batch_size` 默认很小，例如 `1`～`3`
- `usage_probe_force` 默认 `true`（就是为了打穿缓存；仍要错峰）

算法：

1. 每 `interval` 跑扫描器，`max_instances=1`。
2. 取 `list_status_accounts()` 的相关账号。
3. 本轮只处理「到期」的号：`now >= next_probe_at`。`next_probe_at` 首次用 `hash(id) % stagger` 摊开，成功后 `now + interval + 小抖动`，失败后指数退避（封顶例如 6h）。
4. 对到期号 GET `/admin/accounts/{id}/usage?source=active&force=true`（后台「查询」）。不要一次 80 个，也不要用 `usage/batch` 当官方查询。
5. 用返回的 `seven_day` / `five_hour` 写回 extra，重算 `_schedule_state()`。
6. 若 kind 为 `ok` 且 Sub 还挂着 `rate_limit_reset_at` / `rate_limited_at`：POST `/admin/accounts/{id}/clear-rate-limit`，清掉「限流中 / 429」本地锁。401/403/未接码/仍满额不要清。
7. 若 kind 为 `ok` 且 `schedulable is False`：PUT `{ "schedulable": true }`。
8. 若 kind 为 `429` 或 `5h` 且 `schedulable is True`：PUT `{ "schedulable": false }`。5h 不要进踢拉队列。
9. 回写 `ChildAccount.probe_status/label/probed_at`（母号可只打日志，或将来加 Team 字段；不要为母号滥用 child 表）。
10. `invalidate_status_cache()`，让席位页下次能看到「可调度」。

错峰示例（约 50 个号、窗口 60 分钟）：每号偏移 0–59 分钟，扫描器每 1–2 分钟看谁到期，每次 force 1 个。禁止「整点 for 循环打完全部账号」。

干跑：先对**一个**已知重置号调用官方查询，确认百分比会掉到 0 附近。若 Sub 仍显示「限流中」，再打 `clear-rate-limit`。响应不对就停，不要猜。

### 3.2 第 2 层：401 自动重授权

建议设置：

- `auto_reauth_enabled` 默认 `false`
- `auto_reauth_interval_minutes` 默认 `30`
- 浏览器并发 = 1

算法：

1. 从看板状态或第 1 层探测结果收集 `schedule kind == 401` 的子号。
2. `auto_reauth_plan()` 为 `auto=False` 的跳过（母号、Gmail、没代理、没读码），记原因。本地没有密码但 Cloudflare/pickup 可用，仍自动。
3. 已有 running job 的邮箱跳过。
4. 全局一次只跑一个 Playwright。
5. 复用 `_run_auto_reauth_job()` / `run_browser_oauth_reauth()`，不要复制一套浏览器。
6. 浏览器新增 deactivate 识别；返回 `account_deactivated` 后打标，**不要**进重授权重试，交给第 3 层（若第 3 层关着就只告警）。
7. 失败冷却，例如 2–6 小时；`sms_rejected` / `phone_pool_empty` 不要对同一号立刻再来。
8. 成功后走现有 OAuth complete → 推 Sub2API → `probe_access_token`。然后让第 1 层决定是否开调度。

### 3.3 第 3 层：封禁 / 周限满踢拉

建议设置：

- `auto_rotate_enabled` 默认 `false`（必须默认关）
- `auto_rotate_on_deactivated` 默认 `true`（仅当总开关开）
- `auto_rotate_on_weekly_limit` 默认 `true`（仅当总开关开）
- `auto_rotate_force_refill` **必须默认 false**，不要提供「定时强制补位」除非用户以后书面要求

算法：

1. 候选：`account_deactivated` 子号，或探测确认 7d 仍 100% 且已过重置点仍满。
2. 5h 满不是候选。掉票 401 不是候选。
3. 同一 Team 同时只踢 1 个。全场同时只跑 1 条踢拉。
4. `kick_to_standby()`；失败则停。
5. `is_safe_to_refill(vacancy)` 为假：记下 `vacancy_not_safe_to_refill`，**不拉人**。
6. 为真：`invite_and_onboard()`，空邮箱走 HME，号码库接码，`reuse_existing=True` 可先找非冷却 standby，找不到再领新号。
7. 不对账成功不推 Sub2API（现有 onboard 已保证）。
8. 记 `SeatEvent` action=`rotate`，detail 写清原因（deactivated / weekly_limit）。

不要用 `list_due_accounts()` 当本层队列。那是「入组满 7 天」的手动轮转。

## 6. 验收

### 第 1 层

- 单测：错峰偏移覆盖多个 account_id；同一窗口不会选出全部账号；7d 从 100→0 且非 401 时决定开调度；5h 满只关调度；401 不开调度。
- 干跑（需用户同意）：对 1 个重置号 force usage，百分比下降，看板从「429 4天」变为「可调度」或至少不再 100%。
- 日志能看到每个账号的下次探测时间，而不是整点一批打完。

### 第 2 层

- 单测：`auto_reauth_plan` 仍拒绝母号；deactivate 文案 → `account_deactivated`，不再换号。
- 开关默认关。打开后同一邮箱不会并行两个 Playwright。
- 未开开关时行为与现在完全一致（人手点才授权）。

### 第 3 层

- 单测：5h 不满入队列；掉票 401 不入队列；deactivate 入队列；vacancy 不安全则只踢不拉。
- 开关默认关。没有用户确认不得在生产打开。

## 7. 建议开工顺序

1. 只做第 1 层：错峰探测 + PUT `schedulable` + 设置开关 + 单测。
2. 用户确认探测有效后，再做第 2 层：deactivate 识别 + 401 队列（默认关）。
3. 第 3 层最后做，默认关，文档和 UI 写清账单风险。
