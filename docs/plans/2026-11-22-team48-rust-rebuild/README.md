# 计划：team48 用 Rust 重建为纯团队管理

## 需求

现在的 48team-manager 约 9.7 万行，功能堆叠（轮转、号池、Sub2API、收入、服务器浏览器自动化等），大半最近一个多月没用，维护繁杂；服务器自动化始终做不到免接码。新建一个 Rust 项目 `team48` 取代它，只做"纯团队管理"：打开看板就知道每个团队的席位、母号、成员、子号周限额度，自己决定换谁；插件注册的新号经授权桥直接写进 codex-rs（下称 rs）。

项目按"精密零件拼装"组织：一个仓库，两个零件库（官方接口、rs 接口），拼成两个独立小服务（团队看板、授权桥）。以后加功能就继续拼新零件或新小服务，不往已有的东西里塞。老项目先照常跑，新项目可用后一刀切换，再停老项目。

## 对齐结论

| 事项 | 结论 |
|---|---|
| 语言与形态 | 新建独立 Rust 项目（不做 rs 插件、不改进 rs 核心），技术栈参照 rs：axum + tokio + sqlx（运行时查询，不用编译期连库宏）+ SQLite；前端 Vue 3 + Vite（与 rs 一致），构建产物嵌进二进制 |
| 组织方式 | 一个仓库，Cargo workspace：零件 `crates/openai`（官方接口）、`crates/rs-client`（rs 管理接口）、`crates/kit`（加密、配置等公共小工具）；服务 `apps/dashboard`（团队看板）、`apps/bridge`（授权桥）；插件 `extension/` 从老仓库搬来 |
| 团队看板内容 | 团队名、席位、母号（含授权状态）、成员、待接受邀请、手填到期日 |
| 子号额度 | 从 rs 账号列表读，显示成 rs 那样的周限额度条（使用率 %）；5 小时窗口只在出现时如实显示（出现通常意味着席位被改过）；不做任何"该换谁"的推荐或标注 |
| 子号与 rs 对应 | 按"团队官方 ID == rs 账号的工作区 ID"且"官方用户 ID 或小写邮箱一致"双重匹配；对不上显示"未接入 rs" |
| rs 读取失败 | 保留上次数据并标"旧"，不显示成 0% |
| 官方团队写操作 | 邀请（含 Standard / Premium 席位）、踢人、撤回邀请；点了同步等结果，不做后台任务框架；同一团队写操作防重入；超时或 5xx 返回"结果未知"并当场回读名单核对，绝不自动重发 |
| 踢人后 rs | 不动，用户自己处理 |
| 成员同步 | 只在用户点"同步"时读官方接口，不定时同步；同步失败保留旧名单 |
| 母号授权 | 生成 Codex 授权链接、用户手工粘贴回调换令牌，不开浏览器；母号令牌续期由看板服务自己定时做 |
| 授权桥 | 兼容现有插件接口 `/api/ext/ping`、`/api/ext/rs/start`、`/api/ext/rs/complete`：经 rs 代理换令牌，核对邮箱、刷新令牌、Team 套餐后写入 rs；同邮箱已有号只更新凭据并恢复原分组 / 代理 / 并发 / 权重；新号带配置里的首次导入参数 |
| 插件 | 搬进新仓库，只留"直接接入 rs"一种模式；去掉"查 Team48 团队并接入"、指定团队接入、号码池接码；批量注册、HME / Cloudflare 读验证码、唯一 Team 盲选保留；遇手机验证暂停交人工 |
| 将来自动化 | 不做。授权桥的两步接口（start 领链接与代理、complete 交回调）就是通用约定，将来 Python 浏览器自动化当"大号插件"调它 |

**按常规处理的细节**：
- 单个管理员账号密码登录（环境变量配置），会话用签名 Cookie；授权桥用 Bearer 令牌（≥ 24 位才启用，否则 `/api/ext/*` 全部 404），不接受管理员会话。
- 凭据加密沿用老项目的 Fernet 方案（密钥 = `ENCRYPTION_KEY` 的 SHA-256 再做 urlsafe base64），接口只返回"已存 / 未存"，不回显密钥和令牌。
- 母号走自己的代理（加密保存）；官方请求带浏览器 TLS 指纹（Rust 用 wreq），连接按"账号 + 代理"隔离，母号之间不混用出口。
- 危险操作（踢人、撤回邀请、删除本地团队）二次确认，写明是否改官方团队。
- 界面简体中文，时间显示相对时间、悬停看北京时间；桌面优先，手机能看不塌。
- 每个零件和服务有一页说明（做什么、不做什么、对外接口）；服务之间只通过 HTTP 接口沟通，不共享数据库。
- 新项目目录 `C:\Projects\VPS\天理云-美西国际大宽带-8H16G\team48\`，服务器 `/opt/team48-v2`，Compose 项目 `team48v2`，容器 `team48-dashboard`（`127.0.0.1:8028`）、`team48-bridge`（`127.0.0.1:8029`）；切换后 Nginx 把 `48team.xiaozhudf2026.foo` 的 `/api/ext/` 转给授权桥、其余转给看板，插件地址不用改。
- 本机没装 Rust：编译检查在 Docker 里跑（命令见 part-0 定义的 `scripts/check.sh`）。
- 不写测试。

**不做的事**：
- 服务器浏览器自动化（Camoufox / Chromix / Playwright）、rs 邮箱自动授权新号、rs 掉登录自动恢复
- 手动 / 自动轮转、备用号池、rs 自动补号、服务器注册、邀请后自动注册
- Sub2API 全部对接、收入账本、HME 领号、手机号池接码
- 今日切换计数、团队购买信息、Codex 导出、自己探测官方额度、通用自动重授权
- 后台任务框架（Operation / 步骤持久化）、测试
- 改 rs 核心代码（rs 后台"邮箱自动授权"入口的停用在 rs 仓库单独处理，见上线注意）

## 上线注意

- 具体命令以 part-8 产出的 `team48/deploy/cutover.md` 为准。
- **新老并跑期间不得让新项目刷新母号令牌**（新看板设 `MOTHER_REFRESH_ENABLED=false`）：刷新令牌刷一次旧的就作废，两边同时刷会让母号集体掉登录。切换顺序：停老项目容器（或至少关掉它的令牌刷新） → 只读备份老库 `team48.db` → 新项目 `import-legacy` 正式导入 → 启动新看板 → 抽查母号授权状态和一个团队的成员同步。
- 切换 Nginx：`/api/ext/` → `127.0.0.1:8029`，`/` → `127.0.0.1:8028`；`nginx -t` 通过再 reload；插件实测一次直接接入 rs。
- rs 侧：rs 后台"邮箱自动授权"入口调用的是老项目内部接口，老项目停掉后会失效。在 rs 仓库按它的 AGENTS.md 单独停用（隐藏入口或去掉 `fork_team48` 配置段），走 rs 自己的上线流程，不和本计划混做。
- 新项目需加入 rs 所在的 Docker 网络 `codex-proxy-rs_default`（rs 地址 `http://codex-proxy-rs:8080`）。
- 服务器资料库 `C:\Projects\VPS\天理云-美西国际大宽带-8H16G` 的 AGENTS.md / PRODUCT.md / RUNBOOK.md 要把 `/opt/team48` 换成 `/opt/team48-v2` 并更新服务说明（ship 时一起改）。
- 新仓库远端（是否 GitHub、公开还是私有）第一次上线提交时问用户；不得提交 `.env`、`private-config.mjs`、数据库。
- 老仓库 `48team-manager` 切换稳定后归档；其中 `docs/plans/` 下另外两个旧计划（rotation-live-acceptance、desktop-oauth-entry）随之作废，由用户决定是否删除。
- 本计划文件在老仓库里，上线时把新仓库的 PRODUCT / ARCHITECTURE / RUNBOOK 写全（素材来自各 Part 完成记录），计划随老仓库归档。
